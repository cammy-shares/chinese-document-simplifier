# 编辑指南

## 先抓住要说的事

用原文回答：读者现在需要知道什么，或做什么决定？
把对应的事实、问题或结论前移。背景只留下理解它所需的部分。
不要把作者尚在讨论的想法强改成行动指令。

## 常见中文表达怎样改

以下是判断线索，不是禁词表。先核对原文有多少真实信息，再选择改法。

| 问题 | 原句 | 处理示意 |
| --- | --- | --- |
| 动机套话包住动作 | 为持续赋能资料管理，用户可按月导出记录 | 用户可按月导出记录 |
| 动作名词化 | 对失败任务进行重新提交操作 | 重新提交失败任务 |
| 具体功能被抽象词遮住 | 用户可通过按日期查找记录，促进信息价值沉淀 | 用户可按日期查找记录；不虚构保存或复用机制 |
| 同一结论重复 | 记录可导出为 CSV，从而支持 CSV 格式导出 | 记录可导出为 CSV |
| 无依据的夸大 | 新功能将全面解决查找困难 | 若仅表达目标，改成“新功能旨在减少查找困难”，不写成已解决 |
| 指代含糊 | 它处理完成后会通知他们 | 原文没有明确对象时标记待确认，不擅自补成管理员或用户 |
| 多条件挤在长句中 | 仅管理员启用且成员拥有权限时可导出，停用的空间除外 | 按条件、权限、例外分开写，并核对逻辑仍一致 |
| 凭空制造对比 | 这不仅是一次界面调整，更是协作方式的全面跃迁 | 若事实只有界面调整，就只写具体调整；真实对比有信息时保留 |

## 删掉没有信息的外壳

“随着时代发展”“为了持续提升体验”若没有解释本次变化，可以删除。
同一个结论出现多次时，保留最合适的一处。
结尾已经说完，就停；不补一段愿景或“总的来说”。

“显著改善”“全面解决”若原文没有证据，不补造数据。
根据原意改成可观察的变化，或保留为目标并说明尚未验证。
“为了”“旨在”携带目标时可保留，不能因为它听起来抽象就删除真实需求。

## 把抽象关系写清

遇到“赋能”“拉通”“沉淀”“闭环”等词，先看原文有没有具体对象和动作。
有，就写清实际发生的事；没有，就指出信息不足，不凭常识拼出一个流程。
这些词若是正式术语或确有准确含义，可以保留并按读者需要解释。

例如，“优化资料管理体验”只表达目标。
只有原文另有“按日期查找导出文件”的事实，才可改写为具体功能。
不能自行加上“自动归档、智能搜索、跨端同步”。

## 拆解中文长句

先识别主判断、动作、前提与例外，再决定句子怎么拆。
“仅当 A 且 B”不能拆成 A 或 B；“除 C 外”不能删成对所有对象生效。
多重否定如果可以准确还原为肯定句，就还原；可能改变权限或逻辑时保留并标记。
不要把“未获批准前不得开始”改成“批准后必须开始”：许可不等于义务。

说明文可以先给一句通俗解释，再保留必要术语。
解释只用来源明确给出的含义。原文没交代的技术机制先标记，不补造类比或定义。
陌生术语需要解释时允许增加文字，不为了短而删除读者理解所需的信息。

## 翻译腔与概念嵌套

中文工作文档中，长定语、动作名词化和连续抽象名词容易掩盖关系。
先找出主体与动作，再把目的、前提、例外放到它们实际限制的内容旁边。
不要只把长句切成几段，切开后仍要让读者知道谁对什么做了什么。

| 原表达 | 有来源事实时的改法 | 保留边界 |
| --- | --- | --- |
| 对任务执行状态可见性的增强 | 让用户看见任务状态，或直接写已给出的状态展示方式 | 不补造刷新频率或实时推送 |
| 对于由审批延迟所导致的交付时间变更的处理 | 处理审批延迟导致的交付时间变更 | 原因必须来自原文，不把相关性写成因果 |
| 基于对日志进行分析所获得的判断，我们倾向于先检查网络 | 分析日志后，我们倾向先检查网络 | 保留“倾向”，不写成已确定网络故障 |

专业词、API 名称、代码和已有准确的技术定义可以保留。
若原文提供了术语含义，先用普通中文解释，再给名称；含义未给出时不编定义。
英文缩写本身不等于翻译腔，技术准确性比换成表面通俗的词更重要。

## 保留说话人的轻重

“我倾向”“暂时”“可能”“尚未验证”都携带信息，不应作为赘词删除。
用户要正式文档，就减少随意表达；用户要自然表达，就避免客服式热情。
不要统一改成同样长度的句子、固定三段式或口号式排比。
不要为了“像人”加入错字、口头禅、假装随意或没有依据的个人经历。
